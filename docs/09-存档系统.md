# 09 · 存档系统

> 职责：将游戏运行状态序列化到本地文件，并在启动时恢复。**存档系统只负责状态快照、文件读写、数据校验与恢复，不包含任何玩法判定。**
>
> 存档文件：`user://save_data.json`（UTF-8）。
>
> 本期采用单一存档，不支持多存档槽、手动存档槽、导出或导入。

## 1. 核心原则

1. **统一存档入口**：所有系统通过 `SaveManager` 保存和读取游戏状态，禁止其他系统直接读写存档文件。
2. **状态与配置分离**：`.tres` 用于保存开发者配置的静态数据；JSON 只保存玩家的运行状态，不复制完整的对话、物体或事件配置。
3. **状态更新后保存**：自动存档必须发生在对应状态成功更新之后。
4. **恢复优先于界面初始化**：启动时先读取存档并恢复 `GameState`，再根据恢复后的状态初始化场景、交互点和 UI。
5. **不保存可重建数据**：列表、弹窗、动画进度等临时 UI 状态不写入存档，恢复时根据持久化状态重新生成。
6. **存档不判断剧情**：是否解锁内容、事件是否满足条件、完整度如何结算等均由对应系统决定。`SaveManager` 只记录最终状态。
7. **文件写入失败不得伪装成功**：只有确认保存成功后，才能显示「已保存」Toast。

## 2. 存档方式

### 2.1 文件与版本

- 存档路径：`user://save_data.json`。
- 编码：UTF-8。
- 格式：JSON。
- 存档版本字段：`save_version`，当前值为整数 `1`。
- 本期不实现旧版本数据迁移。

启动时：

1. 检查存档文件是否存在。
2. 文件不存在时，初始化新游戏。
3. 文件存在时，读取并解析 JSON。
4. 检查 `save_version` 是否为当前支持的版本。
5. 版本不匹配时，将旧文件备份为 `user://save_data.bak`，初始化新游戏，并输出日志。
6. 文件无法解析或必要字段缺失、类型错误时，按损坏存档处理：保留原文件备份，初始化新游戏，并输出明确的错误日志。

备份操作不得静默覆盖唯一的旧备份。如果已有 `.bak`，应采用安全的替换策略，确保不会因为备份失败而丢失原始存档。

本期只有 v1，不进行复杂的数据迁移。

### 2.2 手动保存按钮

AI 交互界面右下角保留存档按钮，符合决策 D09。

- 点击后立即调用 `save()`。
- 不需要二次确认。
- 保存成功后显示 Toast：「已保存」。
- 保存失败时不得显示成功提示，应输出错误日志，并向玩家提供明确的失败反馈。
- 手动保存与自动保存使用同一套保存逻辑。

## 3. 保存的全部状态

以下字段必须完整保存。新增持久化状态时，必须同步更新存档结构与自检清单。

| 字段 | 类型 | 内容 |
|---|---|---|
| `save_version` | `int` | 存档版本号，当前为 `1` |
| `phase` | `int` | 当前阶段，1 或 2 |
| `current_scene` | `String` | 当前场景 ID，用于恢复位置 |
| `objects` | `Dictionary` | 物体步骤进度：`object_id → 已完成 step ID 列表` |
| `contents_obtained` | `Array[String]` | 已获得内容 ID |
| `contents_fed` | `Array[String]` | 已投喂内容 ID，跨阶段保留 |
| `topics_unlocked` | `Array[String]` | 已解锁话题 ID |
| `topics_completed` | `Array[String]` | 已完成话题 ID |
| `events_completed` | `Array[String]` | 已完成事件 ID |
| `puzzles` | `Dictionary` | 谜题状态：未解锁、可解、已完成 |
| `player_choices` | `Dictionary` | 事件 ID → 选择结果，例如 `"yes"` / `"no"` |
| `truth_revealed` | `int` | 真相暴露度 |
| `completeness` | `float` | 人格完整度 |
| `regions_unlocked` | `Array[String]` | 已解锁区域 ID |
| `opening_read` | `Dictionary` | 两份开场协议各自的已读状态 |
| `flags` | `Dictionary` | 阶段转换等剧情标记 |
| `settings` | `Dictionary` | 音频开关状态 |

### 3.1 数据格式约束

- 所有 ID 必须与项目配置一致。
- `objects` 只记录已经完成的步骤，不保存可重新生成的步骤 UI。
- `puzzles` 使用项目统一定义的状态值，不允许不同谜题自行创造状态名称。
- `player_choices` 保存已经作出的选择，不保存尚未作出的临时选择。
- `opening_read` 按两份开场协议分别记录，避免一份已读导致另一份被误判为已读。
- `flags` 只允许存放需要持久化的剧情状态，不作为绕过正式字段设计的通用临时变量容器。
- `settings` 只保存本期要求持久化的音频开关状态。
- `completeness` 保存实际结算后的值，不在读取时重新发放奖励。
- `contents_fed` 跨阶段永久保留，不因阶段转换清空。

### 3.2 禁止保存的字段

以下机制已删除或不存在，存档中禁止出现相关字段：

- 21 天倒计时。
- 每日任务。
- 当前天数。
- 当前结局。

不得为了兼容旧设计而保留上述字段。

## 4. 自动保存时机

每个保存时机都必须发生在对应状态更新成功之后。

| 序号 | 时机 | 保存要求 |
|---|---|---|
| 1 | 首次调查获得新内容 | 写入新内容获得状态后保存 |
| 2 | 物体步骤完成 | 每完成一个步骤就保存，不等整个物体调查结束 |
| 3 | 投喂结算完成 | 投喂状态与完整度奖励结算完成后保存 |
| 4 | 话题对话完成 | 更新话题完成状态后保存 |
| 5 | 解谜成功 | 写入谜题完成状态及相关解锁状态后保存 |
| 6 | 玩家作出关键选择 | 写入选择结果及其已结算效果后保存 |
| 7 | 剧情事件完成 | 事件效果执行成功并写入完成状态后保存 |
| 8 | 新区域解锁 | 写入区域解锁状态后保存 |
| 9 | 阶段转换完成 | 阶段、区域、完整度等相关状态全部更新后保存 |
| 10 | 点击存档按钮 | 立即保存当前完整状态 |

### 4.1 避免重复保存与状态遗漏

- 多个状态属于同一次操作时，应在这组状态全部更新后保存一次。
- 不得在状态更新之前保存，导致存档记录旧状态。
- 不得在保存成功之前向其他系统宣告存档成功。
- 对于一次操作引发的连续事件，应保证每个事件完成后均有可靠的持久化记录。
- 存档系统不负责判断哪些操作应触发自动保存；各系统在规定的状态更新节点调用统一保存接口。

## 5. 启动与状态恢复

### 5.1 启动顺序

启动时严格按照以下顺序执行：

1. 初始化 `SaveManager`。
2. 检查存档文件。
3. 有效存档存在时，解析并校验数据。
4. 将存档数据恢复到 `GameState` 及各持久化状态管理器。
5. 根据 `phase`、`current_scene` 和已解锁区域恢复场景及交互状态。
6. 根据恢复后的状态初始化 AI 界面、完整度显示、话题列表和投喂列表。
7. 恢复必要的剧情状态，确认没有正在播放的未完成事件。
8. 完成启动后，才允许玩家操作。

恢复过程中不得因为重新初始化 UI 而重复发放内容、增加完整度或重复结算事件效果。

### 5.2 有效存档

启动时存在有效存档：

- 恢复当前阶段和场景。
- 恢复全部内容、投喂、话题、事件、谜题、选择与区域状态。
- 恢复真相暴露度和人格完整度。
- AI 界面显示的完整度必须与存档值一致。
- 根据当前阶段重新生成投喂列表和话题列表。
- 恢复必要的物体步骤状态和协议已读状态。

### 5.3 无存档

首次启动且不存在存档时：

- 初始化新游戏的默认状态。
- 从开场 AI 界面开始。
- 播放眼睛动画。
- 按开场流程展示两份协议。
- 不得将新游戏初始化误认为存档损坏。

## 6. 事件播放中途退出

事件系统与存档系统共同保证：**未完成的剧情事件重进后从头重播，不允许被跳过。**

- 事件进入 `running` 状态后，不立即写入 `events_completed`。
- 只有关联对话正常结束、持久化效果执行成功后，才写入事件完成状态。
- 退出时未完成的事件不属于已完成事件。
- 重进后，事件系统根据已恢复的状态重新检查条件，重新触发符合条件的未完成事件。
- 如果该事件的触发时机是 `on_enter_ai_interface`，仍必须遵循原有触发时机，不能无条件立即播放。
- 事件效果不得因为重播对话而重复结算。

本期不保存逐句对话进度，也不保存临时的事件播放队列。未完成事件通过已恢复的游戏状态重新判定和触发。

## 7. 阶段转换中途退出

阶段转换必须遵循事务式状态更新原则：阶段转换完成前，不得将新阶段作为已完成状态写入正式存档。

建议流程：

1. 开始阶段转换时，记录转换前的阶段状态。
2. 播放阶段转换演出。
3. 执行阶段转换所需的状态修改，包括阶段、区域、话题及完整度校正。
4. 所有转换操作成功后，将 `phase` 更新为新阶段。
5. 清理或重建阶段相关临时 UI。
6. 保存转换完成后的完整状态。

如果在转换完成前退出：

- 最近一次有效存档仍保持转换前的状态。
- 重进后恢复转换前的阶段。
- 事件系统重新检查条件，并按原触发规则重新触发阶段转换事件。
- 不得出现阶段已更新但区域、完整度或事件完成状态仍属于旧阶段的情况。

阶段转换过程中的临时标记只有在确实需要跨系统协调时才写入 `flags`；正常情况下，使用“转换前存档 + 转换完成后存档”即可，不额外设计复杂的中途恢复系统。

## 8. 文件读写与异常处理

### 8.1 保存

`save()` 执行以下操作：

1. 从各持久化状态管理器收集当前状态。
2. 生成完整的存档字典。
3. 写入 `save_version`。
4. 序列化为 JSON。
5. 写入临时文件。
6. 确认写入成功后，再替换正式存档文件。
7. 写入失败时保留最近一次有效存档，输出错误日志并返回失败结果。

不得在写入失败后删除或覆盖唯一有效存档。

### 8.2 读取

`load_save() -> bool`：

- 成功读取、解析、校验并恢复状态时返回 `true`。
- 文件不存在、解析失败、版本不支持或必要字段无效时返回 `false`。
- 文件损坏或版本不匹配时，按照第 2 节执行备份与新游戏初始化。
- 对未知字段不得擅自将其解释为有效玩法状态。
- 读取失败时输出明确日志，指出失败原因。

### 8.3 JSON 与 Godot 数据类型

- 使用 Godot 原生 JSON 序列化能力。
- 存档中的集合只使用 JSON 支持的数据结构。
- 读取后校验字段类型，再注入运行时状态。
- `Array[String]` 在 JSON 中表现为数组，`Dictionary` 表现为对象。
- 不直接将任意 Resource 对象或运行时节点序列化进 JSON。
- `save()` 的实现必须检查文件打开、写入和关闭相关错误。

## 9. 对外接口

| 接口 | 说明 |
|---|---|
| `save() -> bool` | 收集当前状态并写入正式存档，返回保存是否成功 |
| `load_save() -> bool` | 读取、校验并恢复存档；成功返回 `true` |
| `has_save() -> bool` | 判断正式存档文件是否存在 |

补充约束：

- `SaveManager` 是唯一存档文件读写入口。
- 各系统负责维护自己的运行状态，并在状态更新后通知 `SaveManager` 保存。
- `SaveManager` 不调用剧情条件求值器，不执行剧情效果，不决定阶段转换。
- `has_save()` 只判断文件是否存在，不保证文件内容有效；有效性必须由 `load_save()` 判断。
- 手动存档按钮调用 `save()`，根据返回结果显示成功或失败提示。
