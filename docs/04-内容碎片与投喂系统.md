# 04 · 内容碎片与投喂系统

> 职责：统一管理内容碎片的获得、去重、投喂列表、投喂流程与投喂状态。  
> **本系统不负责剧情条件判定，不直接触发剧情事件。** 内容获得、投喂完成等状态变更通过 `GameState` 统一上报，由事件系统负责后续条件检查，详见 `docs/06`。

## 1. 内容分类

本期内容分为四类碎片，话题 `topic` 独立管理，不属于可投喂内容。

| 类型 | ID 前缀建议 | 用途 | 本期实例 |
|---|---|---|---|
| 爱好 `hobby` | `hobby_` | 反映个人偏好，可投喂 | 看电影、甜品、晒太阳、旅行、可爱的玩偶、喜欢的游戏 |
| 经历 `exp` | `exp_` | 记录过去发生的事，可投喂 | 养昙花、早课的早餐时间、一起包饺子 |
| 作品 `work` | `work_` | 女主创作或保存的个人内容，可投喂 | U 盘、手账本、删减的聊天记录 |
| 线索 `clue` | `clue_` | 揭示背景与隐藏信息，默认不可投喂 | 同居第一天、咖喱鸡排蛋包饭 |
| 话题 `topic` | `topic_` | AI 对话入口，永不投喂 | 电影、U 盘等话题入口 |

每份内容使用唯一的 `content_id` 标识。内容的名称、类型、所属阶段、是否可投喂、投喂对话及完整度奖励均由内容数据配置，不在 UI 脚本中硬编码。

话题使用独立的 `topic_id` 管理，遵循 `docs/05` 的话题系统规则。

## 2. 内容数据结构

每份内容使用 Godot 原生 Resource（`.tres`）配置，至少包含以下字段：

| 字段 | 类型 | 说明 |
|---|---|---|
| `content_id` | `String` | 全局唯一内容 ID |
| `content_name` | `String` | 显示名称 |
| `content_type` | `enum` | `hobby`、`exp`、`work`、`clue` |
| `phase` | `int` | 所属阶段 |
| `feedable` | `bool` | 是否允许通过投喂列表投喂 |
| `feed_conditions` | Condition Resource | 投喂前置条件，可为空 |
| `feed_dialogue` | `String` | 投喂时播放的对话 ID |
| `completeness_bonus` | `float` | 投喂成功后增加的完整度，具体结算遵循 `docs/07` |

补充规则：

- `content_id` 全局唯一，禁止重复配置。
- 线索默认 `feedable = false`。
- 话题不使用内容碎片 Resource 进行投喂，独立存储和管理。
- U 盘使用特殊流程，虽然属于 `work`，但配置为 `feedable = false`，通过 `topic_usb` 使用。
- 投喂前置条件只使用项目统一的条件类型，不允许编写专属判定代码。
- `feed_dialogue` 必须引用有效的对话 ID；特殊流程可由其专属配置明确指定。
- 所有内容 ID、所属阶段和奖励数值以 `docs/story` 的内容清单为准。

## 3. 投喂列表（决策 D18）

### 3.1 入口与显示规则

- 入口：AI 界面左下角功能 UI 的「投喂」按钮，详见 `docs/12 §2`。
- 列表只显示同时满足以下条件的内容：
  1. 所属阶段为当前阶段。
  2. 已获得。
  3. `feedable = true`。
  4. 尚未投喂。
- 四项条件必须同时满足。

| 状态 | 列表处理 |
|---|---|
| 尚未获得 | 不显示 |
| 所属阶段不是当前阶段 | 不显示 |
| `feedable = false` | 不显示 |
| 已经投喂 | 不显示 |
| 当前阶段、已获得、可投喂且未投喂 | 显示 |

### 3.2 条目显示

每个条目显示：

- 内容名称。
- 内容类型标签，图标暂时使用文字占位。
- 点击条目后进入投喂流程。

### 3.3 阶段切换

- 阶段切换完成后，关闭或刷新投喂列表。
- 列表重新按新阶段的内容配置生成。
- `contents_obtained`、`contents_fed` 等历史状态永久保留在存档中，不因阶段切换清空。
- 历史状态供事件条件、剧情判断及其他系统查询使用。

### 3.4 模态规则

- 投喂列表打开期间，禁止点击底层界面和世界交互点。
- 关闭列表后恢复进入前的界面状态。
- 投喂流程启动后，列表不得继续接受新的投喂请求。
- 投喂进行中屏蔽其他操作，避免重复提交。

## 4. 投喂流程

投喂必须严格按照以下顺序执行：

1. 玩家在投喂列表中选择一份内容。
2. 系统检查该内容是否已获得；未获得则拒绝投喂。
3. 系统检查 `feedable` 是否为 `true`；否则拒绝投喂。
4. 系统检查该内容是否属于当前阶段；不属于则拒绝投喂。
5. 系统检查 `feed_conditions`；不满足时显示 Toast：「暂时无法投喂」。
6. 系统检查该内容是否已经投喂；已投喂则拒绝重复投喂。
7. 校验通过后锁定投喂操作，自动切换至 AI 界面。
8. 调用 `DialogueManager.play_dialogue(dialogue_id)` 播放对应的投喂对话。
9. 对话正常结束后，写入已投喂状态。
10. 按 `docs/07` 的规则结算 `completeness_bonus`。
11. 发出 `content_fed(content_id)` 信号，通知 `GameState` 更新状态。
12. `GameState` 通知事件系统检查条件，详见 `docs/06`。
13. 保存投喂状态与完整度，刷新投喂列表。

### 4.1 投喂失败与中断

- 前置条件不满足时，不切换界面、不播放对话、不改变投喂状态。
- 投喂对话未正常结束时，不写入已投喂状态，也不结算完整度奖励。
- 投喂过程中退出游戏时，该次投喂视为未完成；重新进入后允许重新投喂。
- 已完成投喂的内容不允许再次投喂。
- 本期不提供已投喂内容的回应回看功能。

### 4.2 投喂状态唯一写入

`contents_fed` 是持久化状态，必须由投喂系统统一维护。

- 普通投喂：对话正常结束后写入。
- 特殊投喂：由对应的特殊流程在规定节点写入，但仍使用统一的状态管理入口。
- 重复提交同一内容时，不重复增加完整度、不重复发放奖励，也不重复发送成功结算。
- 状态写入与完整度结算必须保持一致，避免出现已标记投喂但奖励未结算，或奖励重复结算的情况。

## 5. 分支回应：聊天记录投喂

`work_chat_records` 的投喂对话根据当前 `truth_revealed` 选择对应版本。

| 条件 | 对话 ID |
|---|---|
| `truth_revealed >= 1` | `dlg_feed_chat_records_high` |
| `truth_revealed == 0` | `dlg_feed_chat_records_low` |

实现规则：

1. 在开始投喂对话前读取当前 `truth_revealed`。
2. 按条件选择对应的 `dialogue_id`。
3. 将选中的 ID 交给 `DialogueManager` 播放。
4. 对话系统只负责播放选定的内容，不负责修改条件值。
5. 对话内容必须来自已配置的对话 Resource，不允许程序动态生成、拼接或修改文本。

如果项目统一采用对话变体配置，则可通过 `variants` 实现条件匹配：按配置顺序检查，播放第一个满足条件的变体。若没有任何变体满足条件，应输出配置错误并中止本次投喂，不得随意播放其他版本。

该机制仅用于选择预先配置的对话，不允许在投喂系统中为聊天记录编写专属分支判定代码。

## 6. 内容获得与去重

### 6.1 唯一获得入口

内容获得统一通过以下接口：

`grant_content(ids: Array[String])`

内容来源包括：

- 物体交互步骤的 `grants`。
- 对话完成后的 `on_complete_grants`。
- 事件效果中的 `grant_content`。
- 其他明确配置的奖励来源。

所有来源最终调用同一个获得入口，不得绕过统一接口直接写入 `contents_obtained`。

### 6.2 去重规则

- 以 `content_id` 为唯一依据进行去重。
- 已获得的内容再次发放时，不重复入账、不重复弹出 Toast。
- 一次请求包含多个 ID 时，逐个检查并处理。
- 无效 ID 必须输出错误日志，不得静默创建不存在的内容。
- 发放失败的内容不得写入已获得状态。

### 6.3 获得成功后的处理

每份新内容成功获得后：

1. 写入 `contents_obtained`。
2. 弹出 Toast，显示「材料名称 + 类型」，样式见 `docs/12 §8`。
3. 发出 `content_obtained(content_id)` 信号。
4. 保存获得状态。

如果一次发放多个内容，每份内容分别执行去重与成功处理。

获得内容本身不直接触发剧情事件。`GameState` 收到状态变更后通知事件系统检查条件。

### 6.4 话题解锁

话题不走 `grant_content()`，使用 `docs/05` 定义的话题解锁接口。

新话题成功解锁后：

- 写入 `topics_unlocked`。
- 弹出 Toast：「新话题解锁」。
- 同一话题重复解锁时不重复发放、不重复弹出 Toast。
- 状态变更后通知事件系统重新检查条件。

## 7. 特殊流程：U 盘（`work_usb`）

U 盘不通过普通投喂列表投喂，而是通过话题入口使用。

### 7.1 使用入口

- 获得 `work_usb` 后，由对应事件解锁 `topic_usb`。
- U 盘不显示在普通投喂列表中。
- 玩家通过 AI 界面的「使用 U 盘」话题入口启动对应对话。
- 话题的解锁、显示和重复播放遵循 `docs/05`。

### 7.2 状态联动

- U 盘使用对话正常结束后，将 `work_usb` 写入已投喂状态。
- 状态写入使用统一的投喂状态管理入口。
- `completeness_bonus = 0`，不因使用 U 盘增加完整度。
- 阶段转换时的完整度校正规则遵循决策 D06 与 `docs/07`。
- 重播 `topic_usb` 不得重复执行投喂结算或其他一次性效果。

U 盘使用属于特殊投喂流程，不要求通过普通投喂列表完成，但必须与普通投喂保持一致的状态管理、去重和存档规则。

## 8. 对外接口与信号

| 接口或信号 | 说明 |
|---|---|
| `grant_content(ids: Array[String])` | 统一内容发放入口，负责去重、Toast 与存档 |
| `content_obtained(content_id: String)` | 新内容成功获得后发出 |
| `content_fed(content_id: String)` | 内容成功完成投喂后发出 |
| `is_content_obtained(content_id: String) -> bool` | 查询内容是否已获得 |
| `is_content_fed(content_id: String) -> bool` | 查询内容是否已投喂 |
| `get_feedable_contents() -> Array` | 返回当前阶段已获得、可投喂且未投喂的内容 |
| `feed_content(content_id: String)` | 请求开始投喂；执行校验并启动投喂流程 |

说明：

- `get_feedable_contents()` 只负责返回符合显示条件的列表，不修改游戏状态。
- `feed_content()` 负责校验和启动流程，不直接执行剧情条件判定。
- `content_obtained` 与 `content_fed` 是状态变更通知，不代替状态存储。
- `GameState` 接收到相关通知后，负责更新或确认对应状态，并通知事件系统检查条件。
- `DialogueManager` 不直接写入 `contents_fed`，而是在对话正常结束后通知投喂系统完成结算。
- 所有持久化状态统一由对应系统维护，并由存档系统保存。

## 9. 自检清单

- [ ] 线索不会出现在普通投喂列表中。
- [ ] 未获得的内容不会出现在投喂列表中。
- [ ] 非当前阶段的内容不会出现在投喂列表中。
- [ ] 已投喂内容不会出现在投喂列表中。
- [ ] 投喂成功后条目立即从列表消失。
- [ ] 阶段切换后列表仅显示新阶段符合条件的内容。
- [ ] 阶段切换不会清除历史获得状态与投喂状态。
- [ ] 不满足 `feed_conditions` 时显示 Toast，且不启动投喂。
- [ ] 投喂对话未正常结束时，不写入已投喂状态或完整度奖励。
- [ ] 投喂成功后只结算一次完整度奖励。
- [ ] 投喂状态变更后通知 `GameState`，由事件系统统一检查后续条件。
- [ ] 内容通过不同来源发放时，均调用 `grant_content()`。
- [ ] 重复发放同一内容不会重复入账或弹出 Toast。
- [ ] 话题使用独立的解锁与去重机制。
- [ ] U 盘不会出现在普通投喂列表中。
- [ ] 使用 U 盘的话题对话正常结束后，`work_usb` 标记为已投喂。
- [ ] 重播 U 盘话题不会重复结算。
- [ ] 聊天记录投喂根据当前 `truth_revealed` 播放正确版本。
- [ ] 对话文本完全来自已配置的对话数据，不由程序动态生成或修改。
- [ ] 投喂列表打开时底层不可交互；关闭后恢复进入前的界面状态。
- [ ] 投喂过程中无法重复提交或同时启动其他交互。
- [ ] 获得、投喂与完整度状态均能正确存档并在重新进入后恢复。
