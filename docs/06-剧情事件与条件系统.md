# 06 · 剧情事件与条件系统

> 职责：统一条件求值、事件触发、事件队列调度与剧情效果执行。这是全游戏的核心底层系统。
>
> 事件与条件采用数据驱动，事件配置使用 Godot 原生 Resource（`.tres`），禁止为单个剧情编写专属判定代码。所有条件和效果必须使用 `docs/02 §9` 定义的封闭类型。

## 1. 核心原则

1. **统一检查机制**：调查、投喂、话题完成、选择、解谜、阶段转换等操作改变游戏状态后，由 `GameState` 通知事件系统检查条件。禁止在交互物件、话题按钮或对话脚本中散落剧情判定。
2. **统一条件结构**：所有事件条件使用 `docs/02 §9` 定义的封闭条件类型，并通过 `all` / `any` 组合。所有条件由同一个条件求值器处理。
3. **统一效果执行**：所有剧情效果使用 `docs/02 §9` 定义的封闭效果类型，由统一效果执行器处理。事件配置只能引用已实现的效果类型及其参数。
4. **事件与对话解耦**：事件系统决定何时触发事件、播放哪段对话以及何时执行效果；对话系统只根据 `dialogue_id` 播放对话，不负责判断剧情条件。
5. **表现与状态修改分离**：对话中的立绘切换、黑屏、红色覆盖等表现指令由对话系统协调执行；阶段推进、区域开放、话题解锁、真相值变化等持久化状态修改由事件效果执行器完成。
6. **事件状态唯一管理**：事件的排队、运行、完成状态由事件系统统一维护。其他系统不得直接修改事件完成状态。
7. **单线程串行播放**：同一时刻只允许一个剧情事件处于播放状态。事件播放期间屏蔽玩家的其他操作，防止剧情并发和状态冲突。

## 2. 事件数据结构

每个事件使用一个 Godot 原生 Resource 配置。具体字段可根据项目现有 Resource 结构调整，但必须支持以下信息：

| 字段 | 类型 | 说明 |
|---|---|---|
| `event_id` | `String` | 全局唯一事件 ID |
| `phase` | `int` | 事件所属阶段 |
| `priority` | `int` | 优先级，数值越大越先执行 |
| `order` | `int` | 同优先级事件的排序序号，数值越小越先执行 |
| `trigger` | `String` | 触发时机，例如 `immediate`、`on_enter_ai_interface` |
| `conditions` | Condition Resource | 触发条件，使用 `all` / `any` 组合 |
| `dialogue_id` | `String` | 关联的对话 ID；无对话事件允许为空 |
| `effects` | Array | 对话结束后执行的持久化剧情效果 |
| `once` | `bool` | 是否只允许成功触发一次 |

要求：

- `event_id` 全局唯一，不允许重复。
- `dialogue_id` 必须能被对话系统解析；无对话事件可以为空。
- `conditions` 与 `effects` 必须使用已定义的封闭类型。
- `priority`、`order` 和 `trigger` 必须有明确配置，不得依赖代码中的临时默认判断。
- 不允许在事件 Resource 中写 GDScript 表达式、任意函数名或可执行代码。
- 事件的详细条件、优先级和效果配置以 `docs/story` 中的事件清单为准。

## 3. 事件状态与生命周期

每个事件在运行期间具有以下状态：

| 状态 | 含义 |
|---|---|
| `pending` | 尚未触发，等待条件或触发时机满足 |
| `queued` | 条件与触发时机均满足，已进入队列 |
| `running` | 正在执行事件 |
| `completed` | 已完成对话与持久化效果结算 |

事件处理流程：

1. 玩家操作或系统事件改变游戏状态。
2. `GameState` 通知事件系统调用 `check_events()`。
3. 事件系统求值所有符合检查范围、状态为 `pending` 的事件。
4. 条件与触发时机均满足的事件进入队列，并立即登记为 `queued`，防止重复入队。
5. 事件系统根据优先级和排序序号安排执行顺序。
6. 队列轮到该事件时，将其状态改为 `running`，锁定玩家操作。
7. 如果事件配置了 `dialogue_id`，调用 `DialogueManager.play_dialogue(dialogue_id)` 播放对话。
8. 对话正常结束后，执行事件配置的持久化效果。
9. 效果执行成功后，将事件状态改为 `completed`，发送 `event_completed(event_id)` 信号。
10. 再次调用 `check_events()`，检查本次效果是否满足其他事件的条件。
11. 队列清空后解除事件播放锁，并自动存档。

无对话事件跳过第 7 步，直接执行效果结算。

**重要约束：**

- 只有状态为 `pending` 的事件可以首次入队。
- `queued`、`running`、`completed` 状态的事件不得重复入队。
- `once=true` 的事件完成后永久不再触发。
- `once=false` 的事件只有在明确的重复触发规则允许时才能再次触发，不得因为条件持续成立而无限循环。
- 事件在执行期间不得被其他事件抢占。
- 事件的完成状态必须在持久化效果成功执行后写入。

## 4. 条件检查与事件调度

### 4.1 统一检查入口

统一入口：

`check_events()`

由 `GameState` 在相关状态变更后通知事件系统调用。

需要检查的状态变更包括：

- 调查点完成或获得调查内容。
- 投喂材料及内容解锁。
- 话题完成。
- 玩家作出选择。
- 密码输入正确或解谜完成。
- 阶段转换。
- 玩家进入 AI 界面。
- 其他会影响 `docs/02 §9` 所定义条件的状态变更。

以上操作只负责更新各自所属的游戏状态，不直接判断或启动剧情事件。

### 4.2 条件满足不等于立即播放

事件必须同时满足两个条件才能入队：

1. `conditions` 求值结果为真。
2. 当前时机满足事件配置的 `trigger`。

例如：

- `immediate`：条件满足后即可入队。
- `on_enter_ai_interface`：条件满足后暂不入队，直到玩家进入 AI 界面，才允许入队。

玩家进入 AI 界面时，界面系统只通知事件系统发生了该时机事件。是否播放、播放哪段对话，仍由事件系统统一决定。

### 4.3 多个事件同时满足时的顺序

所有符合条件的事件按以下规则排序：

1. `priority` 降序。
2. `priority` 相同时，`order` 升序。
3. 如果两项仍相同，按事件配置中的稳定顺序处理，不得依赖不确定的容器遍历顺序。

同一时刻只允许一个事件处于 `running` 状态。

多个事件同时满足条件时，必须逐个串行播放，禁止合并对话、并发播放或跳过已排队事件。

如果当前事件的效果解锁了新的事件，新事件经过条件检查后加入待处理队列。当前队列中已经排定的事件不得因级联检查而被无故移除或重复加入。

## 5. 事件清单总览

以下事件的详细条件、效果与优先级以 `docs/story` 两份事件清单为准。

| 事件 ID | 阶段 | 功能 |
|---|---|---|
| `event_unlock_master_bedroom` | 1 | 解锁主卧，条件见 D03 |
| `event_phase1_usb_topic` | 1 | 获得 U 盘后解锁对应话题与使用入口 |
| `event_phase1_end` | 1 | U 盘真相选择结束后播放阶段转换演出，并开放女主房间 |
| `event_photo_wall_talk` | 2 | 调查照片墙后触发 AI 自动对话，包含黑屏闪现 |
| `event_diary_password_hint` | 2 | 满足密码提示条件后触发提示，具体条件见 D04 |
| `event_computer_unlocked` | 2 | 电脑密码正确后播放独白，并显示三个文件夹 |
| `event_ai_after_unlock` | 2 | 满足条件后，在玩家进入 AI 界面时自动搭话 |

新增剧情事件时，应优先扩展 Resource 配置，而不是为单个事件增加专属 GDScript 判定分支。

## 6. 特殊规则

### 6.1 阶段转换事件

阶段转换事件负责协调阶段转换流程。

- 阶段转换演出由关联对话及其表现指令完成。
- `advance_phase` 等效果负责真正修改游戏阶段。
- 阶段切换后的话题列表清理、完整度校正、区域开放等操作遵循 `docs/07 §3`。
- 同一阶段转换只能由一个明确的事件效果执行，禁止对话系统和事件系统重复推进阶段。
- 阶段转换完成后，重新检查受阶段变化影响的事件条件。

### 6.2 话题与事件的关系

- 话题系统负责展示符合当前阶段、已解锁且具有有效 `dialogue_id` 的话题，具体规则见 `docs/05`。
- 玩家点击话题后，由话题系统请求对话系统播放对应对话。
- 话题完成状态由话题系统按既定规则维护；状态变更后通知事件系统重新检查条件。
- 事件系统不得自行重复发放话题内容，也不得因话题重播而重复执行奖励效果。
- 无对话话题如果需要作为后续事件的条件，应按照 `docs/05` 的规则处理其完成状态。

### 6.3 玩家选择

- 选择 UI 与选项显示由对话系统负责。
- 玩家选择结果由既定选择系统记录。
- 选择结果更新后通知事件系统重新检查条件。
- 真相值变化等持久化效果必须通过统一效果执行器执行。
- 同一个选择事件不得因为重复进入或重播对话而重复结算。具体规则见 `docs/05` 与 `docs/07`。

### 6.4 事件播放期间的输入锁定

事件进入 `running` 状态后：

- 屏蔽地图、调查点、投喂入口、话题按钮和其他交互入口。
- 对话推进仍由 `DialogueManager` 正常处理。
- 不允许玩家中途跳过整段事件。
- 事件正常结束并完成效果结算后，才允许消费下一事件或恢复普通操作。

### 6.5 中途退出与重新进入

- 事件播放过程中退出游戏时，该事件尚未完成。
- 重新进入游戏后，该事件从头重播，不允许因为未完成而直接跳过。
- 持久化事件效果默认在关联对话正常结束后执行，因此中途退出不会重复结算这些效果。
- 事件完成状态与已成功写入的游戏状态必须一起保存。
- 自动存档发生在事件效果结算完成后，以及整个事件队列清空后。
- 对话中途的表现指令不作为独立的持久化剧情效果保存。

### 6.6 级联防护

事件效果可能改变状态，并解锁后续事件。为避免配置错误造成无限循环：

- 每次事件效果结算后重新检查条件。
- 同一事件在当前级联处理过程中不得重复入队。
- 单次级联深度上限为 10 层。
- 超过上限时停止继续级联，输出包含事件 ID 与级联深度的错误日志。
- 发生错误时不得将未成功执行的事件标记为 `completed`。
- 修复配置后，应能够从存档状态重新检查尚未完成的事件。

## 7. 对外接口

| 接口 | 说明 |
|---|---|
| `check_events()` | 统一检查符合范围的待触发事件 |
| `event_completed(event_id: String)` | 事件成功完成后发出信号 |
| `is_event_completed(event_id: String) -> bool` | 查询事件是否已完成，供条件求值器使用 |
| `notify_trigger(trigger_id: String)` | 通知事件系统某个触发时机已经发生，例如进入 AI 界面 |
| `start_next_event()` | 在没有其他事件运行时，启动队列中的下一个事件 |

说明：

- `check_events()` 由 `GameState` 在状态变更后调用或通知触发。
- `notify_trigger()` 只通知发生了什么，不直接指定播放哪段对话。
- `start_next_event()` 只由事件系统内部的调度流程调用。
- `DialogueManager` 继续使用 `play_dialogue(dialogue_id: String)` 播放对话，并通过既定的对话完成通知告知事件系统。
- 所有接口只允许通过统一的数据结构和状态查询工作，不得为单个剧情增加专属接口。

## 8. 自检清单

- [ ] 密码提示事件：三份材料投喂与指定话题完成条件必须全部满足；缺少任意一项都不触发。
- [ ] 密码提示事件：满足条件后自动触发且只触发一次。
- [ ] 主卧解锁：缺少任意一项必要交互或投喂条件时不触发。
- [ ] 两个事件同帧满足时，按优先级和排序序号串行播放。
- [ ] 同一事件不会因连续多次调用 `check_events()` 而重复入队。
- [ ] 事件播放期间，玩家不能操作其他 UI 或世界交互点。
- [ ] 对话结束后才执行事件配置的持久化效果。
- [ ] 对话系统只负责播放指定对话，不自行判断剧情条件。
- [ ] 阶段转换效果只执行一次，不会被对话表现指令重复触发。
- [ ] 事件完成状态和对应游戏状态正确存档。
- [ ] 事件播放中途退出并重新进入后，会从事件开头重播。
- [ ] 已经成功结算的事件效果不会因重播对话而重复执行。
- [ ] `on_enter_ai_interface` 事件不会在其他界面提前播放。
- [ ] 事件队列清空后正确自动存档。
- [ ] 级联超过 10 层时输出错误日志，且不会无限循环。
- [ ] 所有事件条件与效果均由统一求值器和执行器处理，不存在单个剧情专属判定代码。
